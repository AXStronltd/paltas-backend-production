# Deploying PALTAS

Two hosts, one domain. The frontend is a static site on **Netlify**; the API is
a container on **Render**; and Netlify proxies `/api/*` through to Render so
that a browser only ever talks to one origin.

```
                         paltas.io
                    ┌───────────────────┐
   a visitor  ──▶   │      Netlify      │
                    │                   │
                    │  /            ──▶ index.html, dashboard/, assets/
                    │  /api/*       ──▶ ─┐  proxy, status = 200
                    └───────────────────┘ │
                                          ▼
                              ┌───────────────────────┐
                              │        Render         │
                              │     paltas-api        │  ──▶  paltas-api-db
                              └───────────────────────┘         (Postgres)
                                          │
                                          ▼
                                    accounts.google.com
```

---

## Why the proxy, and not just two hostnames

Because of one thing: **the session cookie**.

Put the app on `paltas.io` and the API on `api.paltas.io`, and the browser
treats the session cookie as **third-party**. Safari blocks third-party cookies
by default. Chrome is removing them. Firefox partitions them.

The failure is the worst kind there is. Sign-in works perfectly on your laptop
and fails on **every iPhone** — no error, no console message, no failed
request. The cookie is simply never stored, so the next request arrives
anonymous and the person is bounced back to the sign-in screen forever.

Proxying `/api/*` under the app's own domain makes the cookie **first-party**.
`SameSite=Lax` is then correct, nothing blocks it, and there is no CORS
preflight before every request either.

The API works this out for itself. Set `PUBLIC_URL=https://paltas.io/api` and
`APP_URL=https://paltas.io`, and `src/config.js` sees one origin and switches
the cookie to `Lax`. Set `PUBLIC_URL=https://api.paltas.io` and it switches to
`None`, because that is the only thing that could work — it does not quietly do
the wrong one. Both paths are tested in `test/config.test.js`.

## 1. Render — the API

Blueprint → pick the `paltas-backend` repo. `render.yaml` creates the service
**and a new database**.

> It deliberately does not use `paltas-db`. `npm start` runs `prisma migrate
> deploy`, and that database's seed data has an unresolved provenance question.

Values Render will ask for:

| | |
|---|---|
| `GOOGLE_CLIENT_ID` | Google Cloud → Credentials → OAuth client ID |
| `GOOGLE_CLIENT_SECRET` | the same credential |
| `PUBLIC_URL` | **`https://paltas.io/api`** — the proxied path, not the Render URL |
| `APP_URL` | `https://paltas.io` |

`SESSION_SECRET` is generated by Render. `DATABASE_URL` is wired from the
database.

Check it:

```bash
curl https://paltas-api.onrender.com/health
# {"ok":true,"service":"paltas-api","env":"production"}
```

`/health` touches the database on purpose. A service that answers "healthy"
while its database is unreachable has told you nothing worth knowing.

## 2. Netlify — the frontend

Copy `contract/netlify.toml` into the **root** of `paltas-frontend`, beside
`index.html`, and change one line — the Render address in the `/api/*` proxy:

```toml
[[redirects]]
  from = "/api/*"
  to = "https://paltas-api.onrender.com/:splat"
  status = 200
  force = true
```

Then: Netlify → Add new site → Import from GitHub → `paltas-frontend`.
No build command, publish directory `.` — the repo is already the site.

Point `paltas.io` at Netlify. **Do not** give Render a custom domain: the API
is reached through the proxy, and a second public hostname reintroduces exactly
the third-party-cookie problem the proxy exists to avoid.

---

## 3. Google Cloud, once

Under **Authorised redirect URIs**, add exactly — no trailing slash:

```
https://paltas.io/api/auth/google/callback
```

Not the Render URL. The browser is sent to `paltas.io`, Netlify proxies the
callback through, and Render sets the cookie on `paltas.io`. Google compares
this string character for character; a mismatch gives `redirect_uri_mismatch`,
and it is the most common reason a first deployment cannot sign anybody in.

---

## 4. The two lines in the frontend

**Before `assets/console.js`** on each dashboard page:

```html
<script>window.PALTAS_PROMOTIONS_API = "/api";</script>
```

Relative — that is the point. Not `https://api.paltas.io`.

> Not `PALTAS_API_BASE`. That one belongs to the market service, which turns on
> four endpoints this API does not serve yet, and §4c says a failed call offers
> *nothing* rather than falling back — so setting it switches payment selection
> off across the marketplace. See the README.

**And `contract/homepage-feed.html`** pasted into `index.html` before
`</body>` — the one call the carousel is waiting for.

---

## Order

1. Render first, and `curl /health`.
2. Netlify second, with the proxy pointing at the Render address.
3. `curl https://paltas.io/api/health` — this is the proxy test. If it answers,
   the whole arrangement works.
4. Google redirect URI.
5. Sign in, **on a phone as well as a laptop**. The phone is the test that
   matters; it is the one that would have failed.

---

## What to watch after the first deploy

- **CI must be green before any of this.** The 18 end-to-end tests need
  `npx prisma generate`, and the environment this was written in could not run
  them once. They are the only tests that exercise real routes against a real
  database.
- **A Netlify deploy preview shares the production database.** It is a preview
  of the frontend, not of the system. Do not publish a promotion from one.
- **Render's free tier sleeps.** The first request after idle takes a few
  seconds, which on a sign-in looks like a hang. Worth a paid instance before
  showing anybody.
